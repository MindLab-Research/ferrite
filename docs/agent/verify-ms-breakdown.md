## 2. 三个判据的聚合：谁是主因

### 判据 ①：纯带宽地板 vs launch 提交（任务两判据）

```
Σ t_bw   （14.09GB ÷ 7.672TB/s）  = 1.84 ms  =  4.9%   ← 字节完全不是约束
Σ t_launch（6224 × 3µs）          = 18.67 ms = 50.0%   ← 提交半
Σ max(t_bw, t_launch)             = 19.50 ms = 52.3%
Σ 账本实测                         = 37.79 ms
残差（max 之外的核内时间）           = 18.29 ms = 49.0%
```

**⇒ 两个判据都不单独成立**：纯带宽只占 4.9%，launch 占 50.0%，而 **残差（每发核内固定延迟 + 低达成带宽）也占 49.0%**。
**launch 半与 kernel 执行半几乎 1:1** —— 这就是 381GB/s 的唯一解释：**6232 个 tiny kernel，每一个都同时付"提交"和"执行地板"两份钱**。

### 判据 ②：串行链空泡（每 launch 间 1–3µs）

仓库审计给出的正是这个模型（`dspark-perf-400-plan.md §六`）：

```
6232 launch × (2.9µs submit + 3.3µs 最小执行) = 18.1 + 20.6 = 38.7 ms ≈ 实测 37.31ms
每 launch 全价 = 37.31ms / 6232 = 5.99µs   ← 与 2.9+3.3=6.2µs 吻合
```

- 若 6232 发之间**完全可重叠**，链时 = max(Σsubmit 18.1, Σexec 20.6) = 20.6ms；
- 实测 37.31ms ≈ **两者相加** ⇒ **提交与执行几乎不重叠**（依赖串行 + 每发 tail 延迟）。
- ⇒ 判据 ② 成立：**"每 launch 间 ~2.9µs 空泡 × 6224 发 × 40 层"的确是主导项之一**，
  但它与"kernel 自己的最小执行"是**并列**的，不是唯一。

### 聚合结论（一句话）

> **混合主导，且近似 50/50：launch/提交半 ≈ 18.7ms（50%），kernel 执行半 ≈ 18.3~20.6ms（49~51%），
> 纯 HBM 带宽地板仅 1.84ms（4.9%）。**
> 两者是**同一根因的两面**——不是"kernel 写得太差"或"单纯 launch 太多"，
> 而是 **"6232 个 tiny kernel 串行链"**：少发一发就同时省 `2.9+3.3µs`。

## 3. 能指导优先级的两个排序

### 3.1 按"总 ms"排（同时吃两列的最大项）

| 排名 | 族 | 总 ms | 占 37ms | launch 半 | 执行半（残差） | 一刀下去是什么性质 |
|---|---|---:|---:|---:|---:|---|
| 1 | **shared expert** | 10.40 | 27.9% | 3.00 | 7.40 | **合并**（mrows：1000→200 发 + 885→177MB） |
| 2 | **routed experts** | 8.30 | 22.2% | 1.20 | 7.10 | **核效率**（字节不可压，只能换核/tcgen05） |
| 3 | **投影族** | 3.70~8.7 ⚠️ | 9.9% | 6.00 | −2.3 | **合并 / 图化**（V7 口径先定） |
| 4 | MoE gate | 3.44 | 9.2% | 0.60 | 2.84 | **合并**（`ROW_FOLD_GATE` flag 已存在） |
| 5 | hc 链 | 2.96 | 7.9% | 1.20 | 1.76 | **核效率/并发**（53GB/s，纯占用问题） |
| 6 | attention KV | 2.80 | 7.5% | 2.64 | 0.16 | **launch**（`b·m` 单发，grid 已支持） |
| 7 | indexer | 2.50 | 6.7% | 0.69 | 1.81 | 合并（topk 单核地板是硬约束） |
| 8 | all-reduce | 1.40 | 3.8% | 0.72 | 0.68 | 协议地板（只能减次数） |

**top-2（shared + routed）= 18.70ms = 50.1%**；**top-2 + 投影 + gate = 26ms = 70%**。

### 3.2 按"下一步动作"归类（这才是决策表）

| 动作 | 削哪一列 | 覆盖的族（ms） | 上限收益 | 把握 |
|---|---|---|---|---|
| **A. 合并/多行化**（mrows、rows 进 grid、融合） | **两列都削**（launch N↓ + 每发变大后 3.3µs 固定项被工作量吸收） | shared 10.4 + gate 3.44 + attention 2.8 + indexer 2.5 + hc 2.96 | **−12 ~ −16ms** | 高（shared/gate 只差默认值） |
| **B. 图化**（`DSV41_VERIFY_GRAPH=1`） | 只削 **submit 半** | 全部 6224 发 | **−8 ~ −14ms**（上限 = Σsubmit 18.7） | 中高（脚本现成，条件已就位） |
| **C. kernel 效率**（tcgen05/TMA/cp.async） | 只削 **残差半** | routed 7.10 + hc 1.76 | **−5.8 ~ −8.9ms** | 低-中（历史 5 次失败） |

**决策**：
1. **先 A 后 B**：A 是唯一同时压两列的动作，且 shared/gate/attention 都是"代码已就位、只差默认值/A-B"；
   做完 A 后 launch 数从 6224 掉到 ~3000，B 的收益上限也随之从 18.7ms 降到 ~9ms——**顺序反了会浪费 B**。
2. **C 单独排最后**：routed 的 7.10ms 残差只能靠核效率，而字节不可压（30 assign 选 29 唯一专家，去重仅省 3%），
   是全表**唯一没有机械解**的一项。
3. **纯字节/带宽优化（切 head、降精度）优先级最低**：head 是唯一跑满带宽的族（0.86ms 地板 / 1.12ms 实测），
   切它省的是"已经高效的字节"——第二轮实测已证明：**head 切分 −1.5ms 被 a32 的权重重读 +3.9ms 吃光**。

## 4. 两处口径冲突（必须先钉死，否则表会偏）

| # | 现象 | 原因 | 影响 |
|---|---|---|---|
| **⚠️ 投影族** | `t_launch=6.00ms` **> 账本实测 3.70ms** | 账本 §2 的 3.70ms 是 **mrows 口径（~200~520 发）**；审计的 2000 是**逐行口径**（V7：37.31ms 那一次 mrows 到底生效没有，两张证据冲突） | 若逐行：投影族实测应 ~8.7ms，全表 42.8ms 而非 37.31；若 mrows：投影族 launch 半 ≈ 1.56ms。**这一项 ±5ms** |
| **⚠️ norm+cast+quant** | `t_launch=2.04ms` **> 账本实测 0.20ms** | 账本的 0.20ms 只计了 glue/merge，**未含 680 发 rmsnorm/rope/cast 的 launch 成本** —— 这些 launch 的时间被折进了它们服务的族（投影/attention/hc） | 本表把 680 发放在第 11 行只做 launch 计数，**不重复计 ms**（合计仍用账本值） |

**其它 3 个已知不确定项（不改结论方向）**：
- **V2 路由专家 8.30ms ±6ms**（全表最大不确定项）：用的是 rows=1 的 443/286GB/s；`grid.z=rows` 后 CTA 数 ×5，达成带宽可能上移（若到 1.3TB/s ⇒ 2.4ms）。
- **V1 投影族 3.70ms 真值区间 1.6~3.7ms**（mrows 核固定项未实测）。
- **V9 launch 单价**：0.411 / 2.904 / 6.2µs 三选一，同一 6224 发的估价在 **2.6 ~ 38.6ms** 之间——
  **这正是本表把"launch 半"写成 18.7ms 的前提**，必须用图化 A/B 钉死。

## 5. 结语

**回答任务的问题**：verify 37ms 的构成是

- **4.9% 纯带宽地板**（1.84ms，字节完全不是约束）
- **50.0% launch 提交/串行**（18.67ms，6224 发 × 3µs，提交与执行不重叠）
- **49.0% kernel 执行半**（18.29ms 残差：routed 7.10 + shared 7.40 + gate 2.84 + indexer 1.81 + hc 1.76）

⇒ **不是"kernel 效率 vs launch 串行"二选一，而是"tiny kernel 太多"这一件事的两个 50%**。
⇒ **下一步优先级：先"合并"（削两列，top-2 一家 18.7ms），再"图化"扫 submit 尾，最后啃 routed 的核效率。**

## 修正（2026-09-12 perf-only 实测）：launch submit 假设被推翻

**实测**：SH_EXP + GRAPH + ROPE + P3A 全开（ILV=ON，无 e4m3）→ verify = **36.10ms**（vs 基线 37.31ms，仅 −1.21ms）。

图化在 pos=20 捕获成功，50 步平均含 30 步 replay。反推 replay 步时 ≈ 35.5ms vs 裸链 37ms——**图化收益仅 ~1.5ms**。

**结论**：CUDA async launch 已让 CPU submit 与 GPU 执行重叠——**"50% submit + 50% 执行"的分解是错的**（submit 的 2.9µs/launch 只有在 CPU 是瓶颈时才成立）。**verify 的 37ms 几乎全部是 GPU kernel 执行时间**。

**修正后的优化路径**（只有减少 GPU 执行时间才能压 verify）：
1. tcgen05 mxf4（routed experts −6.8ms）——最大单项
2. kernel 融合（减少 kernel 数量降低尾延迟/依赖链）
3. SH_EXP_MROWS 需排查（−8.3ms 预期未兑现——可能 mrows kernel 本身不够快或未正确 dispatch）
4. 图化降级为"正确性工具"（保证 launch 顺序一致）而非性能工具
