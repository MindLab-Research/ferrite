## 0. TL;DR（五条，按重要性）

1. **任务口径的 `p ≈ 0.55` 是低估。** `p/(1-p)` 是**无限长块**的几何和，而我们的块长是 **5**（`DSPARK_DRAFTS`，`config.rs:594`）。
   在 block=5 上：`accept 1.214 ⇒ p = 0.563`（不是 0.548）；**`accept 2.0 ⇒ p = 0.709`（不是 0.667）；
   `accept 3.0 ⇒ p = 0.834`（不是 0.750）**。⇒ **目标比任务书写的更难一档**（§1）。
2. **`accept = 5` 是块长硬上限，`accept = 9`（任务书 §4 的第二档）不存在。** 5 个 draft 全中也只有 5。
   现实外部可达性证明是 **sglang 的 `mean-k ≈ 4.0`（p≈0.93，block 同样=5）**（§3）。
3. **测过的"简单杠杆"全部是同一类（ulp/dtype 级数值对齐），它们的中性/负结果是"这一类不是主因"的证据，不是"天花板"的证据。**
   `DRAFT_HEAD_FOLD v1` 位级一致却中性（`dspark_dev.rs:88-106` 自述 v1 与其替代的 per-row 位级相同）；
   `TAP_BF16+DRAFT_ATTN` 略降。⇒ **近 tie 翻转假说已被证伪**（head 的 logit gap ≫ ulp 噪声）（§2）。
4. **唯一未被测过、且必须先做的实验是「同臂 paired 基线 + 完整 k_acc 直方图」。** 三份记录的直方图形状互相矛盾
   （P(k=0) 在 42%~64% 之间漂移，`dspark-correctness-chain.md:53/774/1738/1646`），**P(k=0) 是「首 token 弱」还是「尾部弱」的唯一判据**；
   在当前口径下，`uniform p=0.563` 预测 P(k=0)=0.437，而实测多落在 0.53~0.64 ⇒ **数据倾向"首 token 集中失败"**（§2.3 / §6-S0）。
5. **任务书 §5 的区分方法（用 `DSV41_DIFF_EAGER` 测 draft vs backbone 的 logits 差异）在当前实现下不可用——
   它比的是 spec 与 eager 两条 backbone，两条都是 44 层主链，与 draft head 无关**（`chain_dev.rs:3440-3560`、`serve.rs:599-620`）。
   正确探针是「oracle tap 对照」：给 draft head 喂**主链自己在该位置的 hidden+token**，看它的 argmax 与主链 argmax 的一致率（§5）。

## 1. 链式失败模型：p 的精算（**先纠正目标口径**）

### 1.1 模型

spec 一步 = draft 提 5 个 token → verify 逐行判 → 接受最长前缀。接受链在**首个失败处 break**
（`chain_dev.rs:7131-7134`：`judges[0]=next`，`judges[1..]=verify_out[..4]`，`k_acc = accept(drafts, judges)`），所以：

```
mean-k = Σ_{k=1..5} Π_{j=1..k} p_j           （p_j = 第 j 个 draft token 与主链一致性）
```

均匀 p 时 `mean-k = p(1-p⁵)/(1-p)`。**关键：块长 5 把求和截断**，而 `p/(1-p)` 是 p⁵ 项被丢掉的无限和。

### 1.2 反解表（本文件的核心修正）

| accept | **均匀 p（block=5，正确）** | 任务书用的 `p/(1-p)` 解 | 差 |
|---|---|---|---|
| 1.022（老基线） | 0.515 | 0.505 | +0.010 |
| 1.067（SEED_POS） | 0.527 | 0.516 | +0.011 |
| **1.214（现状）** | **0.563** | 0.548 | **+0.015** |
| 1.500 | 0.624 | 0.600 | +0.024 |
| **2.000** | **0.709** | 0.667 | **+0.042** |
| 2.500 | 0.777 | 0.714 | +0.063 |
| **3.000** | **0.834** | 0.750 | **+0.084** |
| 3.160 | 0.851 | 0.760 | +0.091 |
| **4.000（sglang）** | **0.927** | 0.800 | +0.127 |

**判定**：任务书 "accept 2.0 需 p≈0.67 / accept 3.0 需 p≈0.75" **系统性乐观 0.04~0.09**。
修正后：**accept 3.0 需要 p=0.83**（正好落回 `accept-gap-1214-to-3.md §4` 的 0.83 一档——两份文档是自洽的，
任务书那句才是近似）。**所以"p 0.55→0.67"不是真正的目标，真正的目标是"p 0.563→0.834"（+0.27 绝对值）。**

### 1.3 单点弹性（决定"先修哪一段"）

均匀模型下 `∂mean-k/∂p` 在 p=0.563 处 ≈ 2.4；但**非均匀**时首 token 的权重大得多：

```
mean-k = p1·(1 + p2 + p2p3 + p2p3p4 + p2p3p4p5)
```

在 `p1=0.56, p2..=0.56` 时，**首 token 的边际系数 ≈ 2.24**（p1 每 +0.1 → mean-k +0.22）。
⇒ **首 token 单点（`drafts[0] vs next`）就是最大的单点杠杆**，而它恰好是整条链里"最不该弱"的一环（§2）。

## 2. p=0.563 的来源分解：数值 / 能力 / 几何

### 2.1 先声明链上两个比较点的物理含义（代码事实）

| 链位置 | 比较 | 左值来源 | 右值来源 | 代码 |
|---|---|---|---|---|
| 第 1 环 | `drafts[0] == next` | **3 层 MTP head** 作用于 tap | **44 层主链** `step_dev` 的 argmax | `chain_dev.rs:7050`, `:7120-7132` |
| 第 j 环 (j≥2) | `drafts[j-1] == verify_out[j-2]` | 3 层 MTP 链（markov 序推） | 44 层主链 m 行批前向 | `chain_dev.rs:7079`, `:7133` |

- draft = 3 层（`n_mtp_layers`，`dspark_dev.rs` 的 `for s in 0..cfg.n_mtp_layers`，`:1320`）+ markov 5 步序推（`dspark_dev.rs:3180-3254`）。
- verify = 主链 44 层的 m 行批前向。
- **第 1 环的右值 `next` 是 44 层主链自己的 argmax**——即 draft 要和主链"抢同一个贪心 token"。

### 2.2 三类根因的可证伪性

| 类别 | 机制 | 已被哪些实验检验 | 结论 |
|---|---|---|---|
| **(a) 纯 ulp/ dtype 数值** | draft/verify 两程序舍入不同 → 近 tie 翻转 | `DRAFT_HEAD_FOLD v1`（**位级一致**，中性）、`TAP_BF16+DRAFT_ATTN`（略降）、`EXPERT_ACT_E4M3`（已同源） | **❌ 证据充分：不是主因**（logit gap ≫ ulp） |
| **(b) 结构化数值（非 ulp）** | TILE vs GEMV 的**求和序/归约树**不同；KV 域（draft f32 vs backbone ring）；draft attention 是独立手写路径 | `ATTN_PROJ_ALIGN`（**重测中，代码注释自述这是"结构性差异"**，`dspark_dev.rs:134-160`） | **⚠️ 未判定——最高先验的结构化嫌疑** |
| **(c) 几何/输入配对** | tap 的层/位置（`TAP_INPUT` 已修一层）、seed 相位（`SEED_POS` 半成品）、块 row-0 的 token、accept 链索引 | `TAP_INPUT`（**唯一 +19% 的杠杆**）、`SEED_POS`（三处不自洽 ⇒ 退化不可归因） | **⚠️ 未判定——但历史唯一有效杠杆落在这一类** |
| **(d) 能力（3层近似44层）** | head 容量不足以复刻主链贪心 | **从未直接测**；只能靠"首 token vs 尾 token 谁弱"间接判 | **⚠️ 未判定——但直方图形状可判（§2.3）** |

### 2.3 直方图是区分 (c/d) 的唯一现成判据（**这条决定了全部排序**）

均匀 p=0.563 的几何分布预测：`P(k=0)=0.437, P(k=1)=0.246, P(k=2)=0.138, P(k=3)=0.078, P(k=4)=0.044, P(k=5)=0.055`。

已记录的三份直方图：

| 来源 | 直方图 | P(k=0) | mean-k |
|---|---|---|---|
| `correctness-chain:53` | {0:124,1:84,2:5,3:15,4:2,5:2} | **0.534** | 0.677 |
| `correctness-chain:774` | {0:55,1:13,2:10,3:4,4:3,5:1} | **0.640** | 0.721 |
| `correctness-chain:1646` | {0:42%,1:29%,2:18%,3:4%,4:4%,5:2%} | **0.42** | 1.067 |

**判定（高置信，推断）**：
- **所有记录的直方图，众数 bin 都是 k=0**（42%~64%，且 mean-k 越低 P(k=0) 越大）。
- 若 (d) 能力主导，则弱环在**尾部**（draft 自己滚 5 步误差累积），P(k=0) 应当**小**（首 token 由 tap 直供，是链上最强的一环）；
  数值上 `p1=0.9, p_j=0.4` 的"头强尾弱"模型给 `mean-k=1.49 但 P(k=0)=0.10`——与实测完全不符。
- 实测 P(k=0)≥0.53（在 mean-k≈0.7~1.2 的臂上）⇒ 拟合需要 `p1≈0.36~0.47`（例如 `p1=0.36, p_j=0.80` 给的正是 `mean-k=1.21, P(k=0)=0.64`）。
- **⇒ 首 token 一致率 p1 ≈ 0.4~0.58，明显低于尾部**。**弱环在"头"，不在"尾"。**
- **而"头"恰恰是能力论最站不住的地方**：第 1 环的输入是**主链自己的 hidden（tap）+ 主链自己的 token**，
  head 做的是"用 (h_i, t_{i+1}) 预测 t_{i+2}"这件被专门训练过的近邻任务，**不需要 3 层去近似 44 层**。
  它弱，只能来自**输入不对**（tap 的层/位置、seed 相位、块几何）或**结构化数值**。

**⇒ 结论（中高置信）：瓶颈在 (b)/(c)，不在 (d)。"3 层 MTP 近似 44 层"不是 1.214 的解释。**

> ⚠️ 该结论的前提是"直方图与 mean-k 同臂"。三份直方图分属不同 arm/版本（`accept-gap §1` U1/U2 早已标注），
> 所以**必须先用 §6-S0 把同臂直方图钉死**，再把这个推断升级为判词。

## 3. sglang 的 p≈0.93：可信度与"同 head"论证

### 3.1 它是硬上界还是软点估计？

| 证据层级 | 内容 | 强度 |
|---|---|---|
| 硬锚点 | LMSYS 一手：`verify = 7.3 ms`（实测） | S |
| 硬推论 | `τ ≥ 383.7 × 0.0073 = 2.80 tok/step` ⇒ **p ≥ 0.72**（block 5） | S（非循环） |
| 软点估计 | 博客自报 `accept length ~5` ⇒ mean-k≈4.0 ⇒ **p≈0.93** | A（自报 + 高接受度工作负载） |
| 独立复现 | GH200：code 3.5~5.05；**loader bug 未修时 1.3~1.8** | A |
| 工作负载敏感 | 同引擎 poetry 仅 ~2.91 tok/step（p≈0.83）；Figure 4 窗口 5.24/3.78/2.91 | S |

**⇒ 正确表述：sglang 的 per-token p ∈ [0.72, 0.93]，随工作负载漂移；0.93 是"高接受度 prompt（16×GSM8K）+ loader 正确"的上沿。**

### 3.2 三条必须说的 caveat（否则对比会误导）

1. **口径不同**：0.93 来自 GSM8K 拼接（低熵、模板化），我们的 1.214 来自**出师表（文言散文，高熵）**。
   同引擎在散文上只有 ~2.91（p≈0.83）、在 prose chat 上甚至更低。⇒ **0.93 vs 0.563 里，至少 0.1 是工作负载差。**
2. **块长其实相同**（sglang DSV4 是 γ=5 / 6 token 步，`dspark-sglang-real-data.md §1.2` 已修正 `DEFAULT_DSPARK_GAMMA=7` 的误读）
   ⇒ **1.66× 的 per-token 差不是块长造成的，全部在 p 上**。
3. **`accept ~5` 不是免费的**：GH200 的 shared-expert 漏 remap 直接把 accept 打到 1.3~1.8——**与我们的 1.214 同量级**
   ⇒ 值得自查"我们是否也有一个类似的 silent loader/mapping 缺口"。

### 3.3 "同一 MTP head"论证站得住吗？

**站得住（对能力论的否定是有效的）**：同一个 checkpoint 的 MTP head，在 sglang 上能产出 τ≈5。
**但它不能证明"数值对齐 = accept 9"**（任务书 §4 第二档）：
- 上限是块长 5，不是 9；
- sglang 的结构优势是 **draft 与 verify 共用同一套 attention backend / 同一量化配置 / 同一 KV 池**
  （`dspark_config.py:26-30`），即"同源数值"——这属于 (b)，不是 (a) 的 ulp 级。

**⇒ 正确的目标形态不是"把 draft 改成官方 f32"，而是"让 draft 与 ferrite 自己的 verify 走同一段数值路径"。**

## 4. 理论天花板：三档估算

### 4.1 上界（数学）

- **绝对上界 = 5.0**（5 个 draft 全中，p→1，仅当模型完全确定）。
- **不可能到 9**（任务书 §4 第二档的 `accept_max ≈ 9+` 是算术错误：block=5，`mean-k ≤ Σ_{k=1..5} p^k < 5`）。

### 4.2 现实天花板（两条竞争假说）

| 假说 | p_max | accept_max (block5) | 触发条件 |
|---|---|---|---|
| **H1 能力主导** | 0.60~0.70 | **1.5 ~ 2.3** | 3 层 head 对 44 层主链的近似极限 |
| **H2 对齐主导** | 0.83~0.93 | **2.96 ~ 4.04** | 几何 + 结构化数值全对齐（sglang 水平） |

### 4.3 本文件的判定

**押 H2（对齐主导），置信度中高**，理由三条：
1. **直方图形状**（§2.3）：弱环在"头"，而"头"是 head 最不该弱的地方 ⇒ 不是容量。
2. **唯一有效的杠杆 `TAP_INPUT` 是几何项**（tap 采集点从层输出→层输入，`chain_dev.rs:11970-11997`），不是数值项 ⇒
   收益来自"输入配对"，与 H2 同源。
3. **sglang 外部存在性**：同一 head、同一块长，达 p∈[0.72,0.93]。

**但 H1 不能被完全排除**：出师表的高熵本身会压低 p（模型对散文的不确定性天然更高），
sglang 在 poetry 上的 2.91 就是"能力 × 工作负载"的联合体现。**H1/H2 的真值由 §5 的判据定。**

**⇒ 现实可达射程：`accept ∈ [1.5, 4.0]`，中位预期 `accept ≈ 2.5~3.0`（p 0.78~0.83）。**

## 5. 区分方法：`DIFF_EAGER` 的局限与正确探针

### 5.1 任务书 §5 的方法在当前实现下**不可用**（这是一个必须纠正的前提）

`DSV41_DIFF_EAGER` 的 `diff_eager_probe`（`chain_dev.rs:3440-3560`，`serve.rs:599-620`）做的事是：
**把 spec 这一轮 emit 的每个位置，用「plain engine 逐行重新 decode」一遍，报告两条路径第一个不一致的位置。**
两条路径**都是 44 层主链**（spec 的 m 行 verify vs eager 的单行 step），**draft head 根本不在这个对照里**。
`DSV41_VROW0_PROBE` 同理（verify row-0 vs eager）。

⇒ **它测的是"主链自身的 m 行/单行一致性"（Backbone self-consistency），
不能区分 "draft 数值不对" 与 "draft 能力不够"。** 任务书 §5 的判据（"差异集中在特定层 → 数值；均匀 → 能力"）
需要一个新的探针才能执行。

### 5.2 正确的区分实验：**oracle tap 对照**（本文件的设计）

**目标**：把"输入错"与"head 弱"分开，这是 H1/H2 的唯一决定性实验。

**做法**（draft 侧已有 dump 设施，`dspark_dev.rs:3179` 的 `dump_unit("logits_row0", …)`；
`unit_dump` + `DSV41_DSPARK_UNIT_INJECT` 已能把 golden 输入注进 draft，`:1148-1167`）：

给 draft head 喂 **主链自己在该位置的 (hidden, token)**——即把 tap/ids/pos 换成主链 eager 单行在**同一位置**的真实值——
然后比较：
1. `draft_argmax` vs `backbone_argmax`（主链 lm_head 在同一 hidden 上的 argmax）；
2. 两者 logits 的归一化差与 top-1/top-2 gap 的分布。

| 观测 | 判定 | 含义 |
|---|---|---|
| **喂对输入后一致率 ≥0.85** | **H2（几何/数值）** | head 没问题；线上 p1≈0.5 是 tap 相位/层/块几何错的 | 
| 喂对输入后一致率仍 ≈0.55 | **H1（能力）** | 3 层 head 对主链贪心的固有偏差 ≈0.45 ⇒ accept 上限 1.5~2.3 |
| 一致率高，但**只在主链 top1-top2 gap 小的位置翻转** | **不可约熵** | 文本本身不确定 ⇒ 天花板由工作负载定，改不了 |
| 一致率高，但**在主链 gap 大的位置也翻转** | **(c) 输入配对** | tap 内容/位置系统性偏（相位假说的干净检验） |

**次选（零新代码，先做）**：
- **单列 p1 与逐环 p_j**：`drafts[0]==next` 的比率（代码里本来就有 `dspark_dump_step`，`chain_dev.rs:7185`）；
  与 `P(k≥j)` 条件下 `drafts[j-1]==verify_out[j-2]` 的比率。**p1 与 p_j 的相对大小直接回答"头弱还是尾弱"。**
- **`ATTN_PROJ_ALIGN` 在正确 binary 上重测**（代码注释自述 TILE vs GEMV 是**结构性**求和序差异，
  `dspark_dev.rs:134-160`；上次 f6062ba4 因 `.so`/binary 不同 commit 而**无效**，`correctness-chain.md:1985-1998`）。
  这是**(b) 类唯一在飞的实验**，判据见 §6-P1。

## 7. 与 400 目标的差距分析

### 7.1 乘积约束（`tok/s = (1+mean-k) × 1000/step_ms`）

| accept | τ=1+mean-k | 400 需要步时 | 现状（33ms lazy） | 备注 |
|---|---|---|---|---|
| **1.214（现状）** | 2.214 | **≤5.54 ms** | 67 tok/s | 低于任何步时地板 ⇒ **400 在 accept 维已出局** |
| 2.0 | 3.0 | ≤7.50 ms | 91 | = sglang verify 实测 7.3ms |
| 2.5 | 3.5 | ≤8.75 ms | 106 | ~L5 地板档 |
| **3.0** | 4.0 | **≤10.0 ms** | 121 | 400 的"刚好"点 |
| **4.0（sglang p）** | 5.0 | ≤12.5 ms | 152 | 400 有余量 |
| 5.0（打满） | 6.0 | ≤15.0 ms | 182 | — |

### 7.2 判定（三条）

1. **单轴都到不了 400**：accept 1.214 即使把步时压到地板也只有 ~295 tok/s（超出部分由 7.3ms verify 硬锚点封死）；
   accept 4.0 停在 33ms 也只有 152 tok/s。**400 = `accept ≥3 且 step ≤10ms`（或 `accept ≥4 且 ≤12.5ms`）。**
2. **accept 的门槛值是 1.92**：`τ < 2.80` 时，即使步时压到 sglang 的 verify 实测下界 7.3ms 也拿不到 400。
   **我们现在 τ=2.214 < 2.80 ⇒ 在"步时无限好"的假设下就已经不可能 400。** 这是"accept 优先"的数学根据。
3. **但 accept 的现实射程只到 2.5~3.0（§4.3）** ⇒ **accept 单独修到头（3.0）也只是把 400 从"绝无可能"变成"刚好可能"**，
   且要求步时同步压到 10ms。**没有"只做 accept 就行"的路径。**

### 7.3 400 的完整等式（引用 `dspark-correctness-chain.md:1814-1818`，本文件复核一致）

```
400 tok/s = accept 3.0 (p=0.834) × step 10.0 ms     ← 两轴都在极限
           或
          = accept 4.0 (p=0.927, sglang 水平) × step 12.5 ms   ← accept 侧需复刻 sglang
当前:      = accept 1.214 × step 33 ms = 67 tok/s       ← 6× 缺口
```

**本战役的现实票面**：`accept 1.5~2.0 × step 15~20ms ⇒ 125~200 tok/s`（`correctness-chain.md:1818` 的 150~250 同量级）。
**400 需要 accept 与步时同时触顶，任一轴停在半途都出局。**

## 8. 一句话交付

> **1.214 对应的均匀 p 是 0.563（不是 0.548）——block=5 的截断让"accept 3.0 需要 p=0.834"而不是 0.75；
> 而且 accept 的数学上限是 5，不是 9。**
> **已测的"简单杠杆"全是 ulp/dtype 级数值对齐，它们的中性/负结果是"这一类不是主因"，不是"到顶"：
> head 的 logit gap ≫ ulp 噪声，近 tie 翻转假说已证伪。**
> **直方图的众数 bin 恒为 k=0（P(k=0)=0.42~0.64）⇒ 弱环在"首 token"——
> 而首 token 是 head 唯一不需要"3 层近似 44 层"的一环（输入就是主链自己的 hidden+token）。
> 所以瓶颈押在「几何/输入配对 + 结构化数值」，不押在「MTP head 容量」。**
> **但这一切的前提是"直方图与 mean-k 同臂"——三份记录互相矛盾，所以第一件事是 S0（同臂 paired 基线+完整直方图），

> 与 draft head 无关，不能用来区分数值与能力。**
> **现实射程 accept ∈ [1.5, 4.0]（中位 2.5~3.0）；400 需要 `accept ≥3 且 step ≤10ms`，
> accept 1.214 下即使步时触地板也只有 295 tok/s ⇒ 两轴必须同时触顶。**
