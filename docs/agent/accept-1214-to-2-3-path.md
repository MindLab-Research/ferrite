## 0. TL;DR（八条，按重要性）

1. **accept 的天花板不是 1.214，是 5。** `DSPARK_DRAFTS = 5`（`dspark_dev.rs:65`），
   `mean-k ∈ 0..=5`。**数字任务实测 `k_acc = 5 5 5 5 5`（`dspark-correctness-chain.md:2257`）
   ⇒ 引擎在结构上没有任何东西把 accept 压在 5 以下。1.214 是一个「任务数」，不是「引擎数」。**
   这一条推翻了「1.214 是天花板」的全部叙事。

2. **用户的「2-3」是「一般散文任务」的口径，且与 sglang 的外部数据完全吻合。**
   sglang 的 Figure 4 工作负载窗口（block 6 = 5 draft + 1 bonus，与我们的上限相同）：
   `gsm8k 5.24 / arena-hard 3.78 / poetry 2.91` tok/step（`dspark-sglang-real-data.md:80`）。
   换算 mean-k：`4.24 / 2.78 / 1.91`。**用户的 2-3 正好落在 sglang 的 poetry↔arena 之间
   ⇒ 2-3 = 「在一般散文上追平 sglang」，不是幻想值。**

3. **1.214 → 2.0 需 per-token `p: 0.563 → 0.709`；→ 3.0 需 `p → 0.834`**（block=5 截断，§2）。
   而 sglang 在 poetry 上 `p ≈ 0.70`、在 arena 上 `p ≈ 0.80`。
   **⇒ 目标 p 的区间精确等于「sglang 在自然散文上的 p」。**

4. **差距集中在「首 token」，而首 token 恰恰是 head 最不该弱的一环。**
   三份直方图众数恒为 `k=0`（`P(k=0) = 0.42~0.64`，§3.3），代码注释实测 `drafts[0] == next 60%`
   （`chain_dev.rs:7294-7295`，154 步 trace）。**首 token 的输入就是主链自己的 hidden(tap) + token，
   head 做的是它被专门训练过的近邻任务，不需要「3 层近似 44 层」⇒ 瓶颈是对齐，不是容量**（中高置信）。

5. **「只修首 token」在数学上不可能到 2.0**（§3.4）：把 `p1` 从 0.60 拉到 1.0、尾部不动，
   `mean-k` 也只到 ~1.49。**必须头尾同时抬**（如 `p1: 0.60→0.85` 且尾部 `q: 0.52→0.61`）。
   这与「整条 draft 链系统性错位（全局校准问题）」一致，而不是「尾部误差累积（容量问题）」。

6. **已测的全部杠杆都是同一类（ulp/dtype 级数值对齐），它们的中性/负结果是
   「这一类不是主因」，不是「到顶」。** `DRAFT_HEAD_FOLD` 位级一致却中性、`TAP_BF16+DRAFT_ATTN` 略降
   ⇒ 近 tie 翻转假说已证伪（head 的 logit gap ≫ ulp 噪声）。真正剩下的是**结构性对齐**与**算法级**两类。

7. **唯一能「机械地」把 p 抬到 0.8+ 的黑马是「宽松接受（top-k / typical acceptance）」。**
   当前接受判定是 exact match（`spec_step.rs:100` 的 `==`）。改成「draft 落在 target 的 top-k 内即接受」
   可直接抬高 p——**但有输出质量代价**（committed 文本不再等于贪心输出），
   **属于算法/策略变更，须由用户/尚书省仲裁，工部不自行决定。**

8. **在出师表本身上，2-3 位于「现实射程的远端」；在一般对话/散文任务上，2-3 是现实目标。**
   判断「2-3 是否已达成」的**前置动作是先测一个中等熵任务**（对话/代码）的真实 accept——
   **这个数我们从来没测过**（§6）。

| **2.000** | **0.709** | | **+0.146** |

> 对照任务书草稿的近似值（`p≈0.55→0.67`）：**偏乐观 0.04~0.09**（`accept-ceiling-analysis.md §1.2`

### 2.1 单点弹性（决定「先修哪一段」）

`mean-k = p1·(1 + p2 + p2p3 + p2p3p4 + p2p3p4p5)`。在 `p1=0.56` 附近，
**首 token 的偏导系数 ≈ 2.24**（`accept-ceiling-analysis.md §1.3`），
比尾部任何一环都大 ⇒ **首 token 是最大的单点杠杆**，而它恰好是最不该弱的一环（§3）。

## 3. 差距的结构：p 的增量怎么分配

### 3.1 两个竞争假说（沿用既有判词）

| 假说 | 机制 | p 的上限 | accept 上限 |
|---|---|---|---|
| **H1 能力主导** | 3 层 MTP 对 44 层主链的近似极限 | 0.60~0.70 | 1.5 ~ 2.3 |
| **H2 对齐主导** | 几何/输入配对 + 结构化数值错位 | 0.83~0.93 | 2.96 ~ 4.04 |

**若 H1 为真 ⇒ 出师表上 2-3 永不可达；若 H2 为真 ⇒ 2-3 可达且有余量。**
**区分它们的唯一决定性实验是「oracle tap 对照」**（`accept-ceiling-analysis.md §5.2`）：
给 draft 喂主链自己在该位置的 `(hidden, token)`，看 draft argmax 与主链 argmax 的一致率。
≥0.85 ⇒ H2；仍 ≈0.55 ⇒ H1。**此实验尚未做。**

### 3.2 现有证据倾向 H2（中高置信）

1. **数字任务打满 5.0** ⇒ head 容量足以做满接受（在低熵任务上）。
2. **唯一 +19% 的杠杆 `TAP_INPUT` 是几何项**（tap 采集点从层输出→层输入），不是数值项。
3. **直方图众数为 k=0**（弱在头，头是 head 最不该弱的地方）。
4. **sglang 外部存在性**：同一 head、同一块长、同一 γ，在 arena 上达 2.78。

### 3.3 首 token 弱 = 全局错位的证据（代码级）

- **代码注释记录实测**：`drafts[0] == next 60%`（`chain_dev.rs:7294-7295`），
  并明确写出 **「the draft block sits at the anchor's OWN position, so drafts[j] predicts pos+1+j」**
  ——这正是 `accept-gap-1214-to-3.md §2.3` 判定的「legacy 臂内容超前 1 格」的现场自述。
- **三份直方图**（`correctness-chain:53/774/1646`）`P(k=0) = 0.534 / 0.640 / 0.42`，
  众数恒为 k=0。均匀 `p=0.563` 预测 `P(k=0) = 0.437` ⇒ **实测 k=0 系统性偏多**
  ⇒ 首 token 被拒的概率高于尾部 ⇒ 弱环在头。

### 3.4 【关键数值结论】只修首 token 到不了 2.0

用 `(p1, q)` 模型（`q` = 尾部各环的均匀命中率），反解 `mean-k`：

| 场景 | p1（首 token） | q（尾部） | mean-k |
|---|---|---|---|
| 现状（拟合 1.214） | 0.60 | 0.52 | 1.20 ✓ |
| **只把首 token 拉到 1.0**（尾部不动） | 1.00 | 0.52 | **1.49** ✗ 到不了 2.0 |
| 只把尾部拉到 1.0（首 token 不动） | 0.60 | 1.00 | 1.60 ✗ |
| 头尾齐抬 | 0.85 | 0.61 | **2.00** ✓ |
| 头尾齐抬 | 0.90 | 0.70 | **2.50** ✓ |

**⇒ 结论（高置信）：到 2-3 需要「首 token 与尾部同时、同幅提升」，
这正是「整条 draft 链被一个系统性错位压制」的指纹，而不是「尾部误差累积」的指纹。
它与 §3.3 的相位/几何错位、以及 sglang 的「draft/verify 同源」结构优势方向完全一致。**

**负面清单（不要投）**：
- **继续修 `SEED_POS`**：三处不自洽（`accept-gap §2.4`），预期仍退化；正确臂是 `SEED_ALIGN`/`SWALLOW`。
- **继续做 ulp 级对齐**：已证中性/负（§4-(a)）。
- **调大 draft 上下文窗口**：`window_size = 128`（`config.rs:528`）= sglang 的 SWA128，
  **已与模型训练时的注意力跨度一致**；调大 = 偏离训练分布，不是杠杆。
- **温度/采样策略**：当前是贪心（argmax），**贪心本身就是 exact-match 判据下的最大 accept 选择**；
  引入采样只会降 accept。无关项。
- **靠加块长提升 accept**：见 §5.2。

### 5.1 关于 P5（宽松接受）——**必须显式上报，工部不自行决定**

- **代码事实**：接受判定是**逐 token exact match**（`spec_step.rs:100`：`drafts[matched] == judges[matched]`）。
- **机械效果**：若把判据放宽为「draft ∈ target 的 top-k」，则任何「draft 是 target 的 #2/#3」的
  拒绝都会被接受，p 直接抬升。这是**唯一不依赖模型/几何修复就能到 2-3 的杠杆**。
- **代价（硬）**：committed 文本**不再等于贪心解码输出**。对出师表（背诵）这类任务，
  top-2 可能仍是「合理的字」但不是「正确的字」⇒ **质量回归**。
- **判定**：这是**策略/质量权衡决策**，不是工程实现。**须用户或尚书省拍板**；
  工部可先做**零风险探针**：dump「draft token 在 target 分布中的排名」直方图，
  量化 top-2/top-3 能回收多少 p——**只读，不改判定**。

### 5.2 关于块长（`DSPARK_DRAFTS`）——不是当前杠杆

`mean-k = Σ_{k=1..N} p^k` 随 `N` 单调升，但**在当前 p 下几乎无效**：

| N | p=0.563 | p=0.834 |
|---|---|---|
| 5（现状） | 1.214 | 3.00 |
| 6 | 1.245 | 3.33 |
| 8 | 1.276 | 3.82 |

**⇒ 当前 p 下加块长只 +0.03~0.06（可忽略），且 verify 成本线性上升
（tok/s 反而下降）。块长只在「p 已高」时才放大 p 的收益——所以 P1/P2 优先，块长最后考虑。**

## 6. 不同任务类型的 accept 预期（本文件的核心交付表）

以「数字任务 5.0」为上限锚点、以「出师表 1.214」为下限锚点、以 sglang 的同口径窗口为外部参照：

| 任务类型 | 熵 | ferrite 现状 | sglang 实测（同口径） | 修完对齐后（H2）预期 | 说明 |
|---|---|---|---|---|---|
| **计数 / 数字 / 模板化** | ~0 | **5.0（已实测）** | 5.24（gsm8k） | 5.0（已到顶） | 上限，无可再提 |
| **代码生成** | 低-中 | **未测** ⚠️ | 3.5~5.05（code review） | 3.5~5.0 | **DSpark head 是按 Code 微调的**（`sglang-real-data §1.4`）|
| **一般对话 / 说明文** | 中 | **未测** ⚠️ | **2.78（arena-hard）** | **2.5~3.0** | ← **用户「2-3」的落点** |
| **中文散文 / 诗歌** | 高 | **未测** ⚠️ | 1.91（English poetry） | 1.5~2.0 | 出师表的同熵类 |
| **出师表（文言+罕见字）** | 高 + 长尾 | **1.214** | —（无同文本数据） | 1.5~2.0 | 当前基线 |

**三条判定：**

1. **「2-3」是一般对话/代码的口径，不是出师表的口径。** 在出师表上，即使复刻 sglang 的高熵表现，
   现实落点是 **1.5~2.0**；要到 2-3 只有两条路：**(a) P5 宽松接受**（质量代价），
   或 **(b) 出师表的熵其实低于 English poetry**（可能——文言高度格律化，但对偶/套语处 prior 极高，
   罕见字/专名处 prior 极低，是**双峰分布**，不是均匀高熵）。
2. **数字任务的 5.0 是「管道无结构缺陷」的证明，但它不能证明「对齐已达 sglang 水平」**——
   因为数字任务太容易，p 天然 →1，无论几何对没对齐都能打满。
   **⇒ 必须用中等熵任务（对话/代码）做验收基准，数字任务不能当**
   （它会掩盖一切对齐缺陷）。
3. **跑一个中等熵任务的 accept，是回答「2-3 是否已达成」的前置条件**——
   在此之前，任何「1.214→2-3 需要什么」的结论都在出师表这一个高熵样本上外推，风险很大。

| accept 2.0 @ 12.5ms | 240 | ✗ |
| **accept 2.5 @ 10ms** | **350** | ✗（差 14%）|
| **accept 3.0 @ 10ms** | **400** | ✓（两轴同时触顶）|
| accept 5.0 @ 15ms（数字任务） | **400** | ✓（步时 ≤15ms 即可）|

**⇒「accept 2-3」单独不足以拿 400**（2.5 时还需步时 ≤8.75ms）；
但 **accept 2-3 + 步时 10ms ⇒ 300~350 tok/s**，是 realistic 的下一档目标。
**400 的真实门槛仍是 `accept ≥3 且 step ≤10ms`（或高接受度任务上 accept 5 + step ≤15ms）。**

## 9. 一句话交付

> **1.214 不是天花板——数字任务实测 5.0（块长上限），引擎结构上没有把 accept 压在 5 以下的东西。**
> **用户的「2-3」是「一般对话/散文任务」的口径，与 sglang 的 arena-hard（mean-k 2.78）完全吻合；
> 在出师表这种高熵文言上，现实落点是 1.5~2.0。**
> **到 2-3 需要 per-token p 从 0.563 抬到 0.71~0.83（+0.15~0.27），
> 且必须首 token 与尾部同时抬——这是「整条 draft 链被系统性错位压制」的指纹，不是「3 层近似 44 层」的指纹。**
> **已测的 ulp/dtype 级杠杆全部中性/负 ⇒ 排除 (a) 类；剩下的是 (b) 结构化数值、(c) 几何配对、
> (e) 算法级（宽松接受）三类。**
> **可行路径：S0 口径 → P1 SEED_ALIGN/SWALLOW（唯二 = 官方几何、从未测）→ P2 draft e4m3 →
> P3 oracle 判 H1/H2 → P4 同源数值 →（若 H1 成立）P6 加深 draft。
> 另有 P5「宽松接受 top-k」是唯一机械可达 2-3 的杠杆，但有输出质量代价，须用户仲裁。**
> **最关键的前置动作：测一个中等熵任务（对话/代码）的 accept——数字任务会掩盖一切对齐缺陷，
> 不能当验收基准。**
